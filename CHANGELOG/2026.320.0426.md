**Provisioning had a verb; teardown had none.** `charly remove` stopped the container, deleted the quadlet
and dropped the deploy entry — and left every podman secret the same deploy created in the engine store
forever. Filed with its RCA as opencharly/plugin-deploy-pod#64, measured on a disposable bed:

```
$ charly remove pod-secret-diag
Removed /home/atrawog/.config/containers/systemd/charly-pod-secret-diag.container
Reloaded systemd user daemon
$ charly status pod-secret-diag --json
{"status":"not configured","container":"charly-pod-secret-diag",
 "secrets":["charly-pod-secret-diag-webui-secret-key"]}          ← the engine object outlives the deploy
```

The residue is not cosmetic: on a shared host it is indistinguishable from a live deployment's secret, and
the next run of the same bed REUSES it ("kept (already provisioned)"), so a stale value can mask a
provisioning defect across runs.

### What the cleanup removes, and what it deliberately does not

| object | teardown now | why |
|---|---|---|
| the engine-side podman secrets `charly-<box>-*` (required, accepted and auto-generated, sidecars included) | **removed** | they are this deploy's own engine objects and nothing else references them |
| the **credential store** entry (`charly/secret/…`, `charly/api-key/…`) | **untouched** | the coordinate may serve other deployments (opencharly/pod-openwebui#19) — tearing one deploy down must never erase a credential another resolves |
| the engine secrets of another **deployment of the same box** | **kept, with a warning** | podman secret names are box-scoped (`charly-<box>-<slug>`), so the cleanup fires only when this is the last deployment of that box in `charly.yml` |
| anything at all, when the engine cannot be enumerated | **nothing, with a warning** | a shared secret is not recoverable; "cannot prove there is no sibling" is not "there is none" |

Two call sites, both the full-teardown branches (quadlet and direct) — `--keep-deploy` keeps the deploy
configured and therefore keeps its secrets, which is what `charly start` needs afterwards.

### Round two: the sibling question is answered from the deploy ENTRIES, not container names

Round one's block was right, and it exposed the deeper fault: **no container-name scan can answer this.** The
three names that must be told apart are

```
charly-<box>                 the DEFAULT deployment   (no trailing dash)
charly-<box>-<instance>      a NAMED instance
charly-<box>-<sidecar>       a SIDECAR of this very deploy
```

so `HasPrefix(n, "charly-<box>-")` misses the default (removing `app/blue` while `app` is configured
deleted the secrets `app` still needed) **and** mistakes our own sidecars for siblings (a default deploy
with sidecars would never clean up). The guard now reads the host deploy config's entries
(`box` = default, `box/<instance>` = named), the only source that knows what is deployed and what is a
sidecar of it; an unreadable config still refuses, with a warning.
