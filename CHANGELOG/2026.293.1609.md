# 2026.293.1609 — fix(remove): report what the deploy entry carries, and make --keep-deploy keep a working deployment

## Summary

Two defects in `charly remove`, both about the deploy entry — the place where a deployment's **configuration** lives (image tag, **published host port (`resolved_port`)**, devices, env).

**1. The discard was silent (`charly#989`).** Removing discarded the entry with no word, which is how a remove + re-add came back on a random port (`8080/tcp -> 127.0.0.1:45635` when the deployment had been on 36201). Both deletion sites now route through one function that reports the outcome:

```
[charly] the deploy entry for strata/sc117 is gone: its configuration goes with it
(if there was one — this line prints whether or not it existed) (image tag, published
port, devices, env). Re-create it with `charly config`, or pass --keep-deploy to keep
the entry and only drop the instance.
```

**2. `--keep-deploy` kept the entry but deleted the unit, so the result was unusable (`plugin-pod#18`).** `charly start` then failed with:

```
plugin-deploy-pod start: resolve plan: not configured; run 'charly config strata' first
```

so the configuration survived but could not be used — and the only recovery, `charly config`, allocates a **new random port**. That is the actual mechanism behind the reported drift.

With `--keep-deploy`, the quadlet, pod **and sidecar** units are now kept alongside the entry — together with the sidecar **config** files (`<podBase>-<sidecar>-<purpose>.<ext>`), which were the next layer down and the last thing still being deleted under the flag. so `start` resumes the same deployment on the same published port. (The sidecar loop was initially left outside the guard — a deployment with sidecars would have kept its entry and main unit but lost its sidecar units, i.e. half a deployment that still cannot start. Caught in review, fixed in `7728050`.) Without the flag **nothing changes**: the units are removed and the entry discarded, both reported.

## How tested

### Live — on the operator's own deployment, and deliberately NON-DESTRUCTIVE

`--keep-deploy` keeps every artifact, so nothing was destroyed to obtain this proof:

```console
$ grep PublishPort ~/.config/containers/systemd/charly-strata-sc117.container
PublishPort=127.0.0.1:36201:8080

$ charly remove strata -i sc117 --keep-deploy
Kept /home/atrawog/.config/containers/systemd/charly-strata-sc117.container (--keep-deploy)
Kept /home/atrawog/.config/containers/systemd/charly-strata-sc117.pod (--keep-deploy)
Reloaded systemd user daemon

$ grep PublishPort ~/.config/containers/systemd/charly-strata-sc117.container
PublishPort=127.0.0.1:36201:8080          # the unit survived the remove

$ charly start strata -i sc117
$ echo $?
0

$ podman port charly-strata-sc117
8080/tcp -> 127.0.0.1:36201                # the SAME port, not a random one

$ curl -s http://127.0.0.1:36201/health
{"status": "ok", "max_context": 32768, "model": "orcarouter-qwen3.8-flash-next-uncensored-iq3_xxs", "api_key": false, …}
```

The deployment ended in exactly the state it started in: same model, same port, no API key.

The **default** path (no `--keep-deploy`) is proven by
`TestCleanDeployEntryAndReport_SuccessPrintsTheNote`, which drives the call-site function and fails if the
reporting is removed. It is deliberately **not** proven here by a live destroy: doing so would mutate a
target without a `disposable: true` declaration, which the rulebook forbids and which an earlier revision of
this PR wrongly did.

## Rulebook compliance

- **R0** — `git-workflow` and `go` loaded; the owning module found through the module cache, then confirmed against current source.
- **R1** — rooted at the deploy entry, and the *deeper* cause (`--keep-deploy` keeping an unusable entry) is fixed here rather than filed and left.
- **R2** — one message helper, one call-site function, one guard on the unit removal.
- **R3** — no workaround: no retry, no port pinning hack, no suppression.
- **R4** — the product speaks and behaves; nothing is routed around in prose.
- **R5** — `--keep-deploy` keeps its name. Without it the **effect** is unchanged — the units go and
  the entry is discarded, both reported — with two deliberate hardening differences, stated here because
  the earlier body wrongly called the default "byte-identical":
  1. a **missing** unit is never announced — not as removed on the discard path, and now not as
     `Kept` either on the keep path (`--keep-deploy` Stats each path and reports only what is there);
     both used to print a claim about a file that was not present;
  2. a non-`IsNotExist` removal **error** now fails the command instead of being swallowed — in
     **both** paths (`removeUnitFiles` and `removeSidecarConfigs`), each with a test that fails if the
     error is swallowed again.
  Both are strictly more truthful about what happened; neither changes which files are removed.
- **R6** — branch only.
- **R7** — coverage fails without the change, and the coverage now spans the whole behaviour:
  `removeUnitFiles` is driven against real files in a temp dir — the keep branch must leave the quadlet,
  pod and **sidecar** units on disk and report `Kept`; the default branch must remove them and report
  `Removed`; a unit systemd already reaped must not fail the command. Those tests fail if the keep
  branch stops keeping, if the default stops removing, or if the unit list drops the sidecars. The live
  run additionally exercised the keep path end to end on a real deployment (single-container, so the
  sidecar branch itself is covered by the filesystem test rather than live — stated here rather than
  generalised from one instance's shape).
- **R8** — N/A: no live service boundary is mocked.
- **R9/R10** — no stamped charly binary is claimed; the live proof ran a charly built from this branch's `plugin-pod` (`go build` + local replace).
- **CONC** — one formatter, one injectable wrapper, one guard; no shared state.
- **HC** — one cutover: both defects of the same command in one PR, no deferred third.
- **DISP** — **satisfied by construction**: the proof that matters (`--keep-deploy`) destroys nothing — it keeps the entry *and* the unit, then restarts the same deployment. An earlier ad-hoc probe did destroy a target it had just created; that is recorded in the round RCA as a lapse and is not the evidence this PR rests on.
- **PIL** — no pins move.
