# 2026.296.1416 — feat(pod): consume the sdk selection resolvers for every engine read (#25)

## Summary

Migrates `plugin-pod` onto the sdk's ONE selection model. Every site that read `rt.RunEngine`, called the divergent sdk engine lookup, or picked an engine by hand now calls `deploykit.ResolvePodEngine` + `deploykit.ResolveContainerdTarget` through one `resolvePodSelection` (`selection.go`).

### Per-site migration (old → new)

| Site (pre-change `origin/main` `f8f0ae4`) | Old | New |
|---|---|---|
| `remove_orchestration.go:425` | `runEngine := rt.RunEngine` + a hand-rolled `dc.Lookup(...).Engine` override + silent unset fallback | `resolvePodSelectionFor` (the precedence is the resolver's) |
| `pod_cmd.go:323` (`VolumeListCmd`) | `kit.EngineBinary(deploykit.ResolveBoxEngineForDeploy(..., rt.RunEngine))` | resolved selection's binary |
| `pod_cmd.go:366` (`VolumeResetCmd`) | same | same |
| `service_resolve.go:66` | `deploykit.ResolveBoxEngineForDeploy(..., rt.RunEngine)` | resolved selection threaded to `validateServiceName` + `buildServiceArgv` |
| `remove_tunnel.go:35,39` | `container.ContainerImage("podman", …)` + `ExtractMetadata("podman", …)` | the resolved engine word (each probe resolves its own binary) |

Deleted in the same cut: the hand-rolled deploy-entry-else-runtime lookup and the unset engine fallback. No second selector and no engine literal remain (grep pasted below).

Behaviour this changes (each pinned by a test that fails on the pre-change tree):

1. A retired/unknown engine word is now a hard error. On the pre-change tree `kit.EngineBinary("nerdctl")` resolved to `"podman"` and `kit.EngineCapabilityFor("nerdctl")` answered `{Name:"podman"} ok=true` — a `nerdctl` deploy silently ran podman.
2. A deploy entry's `rootful:` word is validated (the target resolution is reachable, not a computed-and-discarded value); the pre-change lookup ignored rootful entirely.
3. An unreadable per-host overlay is an explicit error on the volume/service selection paths. `charly remove` resolves ONE teardown selection and shares it with the tunnel read: it degrades visibly to the env/settings fold ONLY for an unreadable overlay (an orphaned deploy must still be torn down), and a readable overlay with a retired engine word is a hard error BEFORE anything is torn down — on the tunnel path too.

Image staging: this plugin carries no staging path (no `load`/`pull`/`import`/`tag` site); the only engine-by-hand image site is the tunnel label read in `remove_tunnel.go`, now on the resolved engine. `deploykit.ResolveImage` is therefore not substituted — there is nothing for it to replace, and fabricating an image-store call for a label READ would add semantics the site does not need.

Pins: `github.com/opencharly/spec v0.2026296.1036`, `github.com/opencharly/sdk v0.2026296.1207`.

Diff surface: `selection.go` (the one consumer), `remove_orchestration.go`, `pod_cmd.go`, `service_resolve.go`, `remove_tunnel.go` (the migrated sites + corrected comments), `selection_test.go` (the controls), `go.mod`/`go.sum` (the pin bump).

### Round 1 — validator BLOCK, RCA, and disposition

The first verdict BLOCKed on two findings. RCA of each, and the missed control:

1. **Overlay boundary in `resolvePodSelectionFor`.** RCA: the new central loader call discarded `loadPodDeployConfig`'s error and leaned on `spec.DeployConfig.Lookup` being nil-receiver-safe (`spec/deploy_config.go:46` guards `dc == nil`). The missed control: `selection_test.go` proved the happy-path precedence but never exercised the OVERLAY BOUNDARY (absent config, unreadable config), so neither the nil path nor the error path could go red. Root fix: an explicit nil-config guard in `deploySelection`, error PROPAGATION in `resolvePodSelectionFor`, a visible-warning fallback in `runPodRemove` (teardown of an orphaned deploy must still run — the pre-existing best-effort contract), and `TestResolvePodSelectionForHandlesNilAndUnreadableOverlay`. The "can panic" half is rebutted: `Lookup` is nil-safe; the untested boundary and the discarded error were real and are fixed.
2. **Probe input, word vs binary.** The block proposed passing `sel.binary()` to the container/image probes. The control written for it shows the opposite: the probes call `EngineBinary` themselves, so the WORD is correct (`nerdctl` for containerd), while handing them the BINARY makes that resolve fall back to `podman` (`kit.EngineBinary("nerdctl") == "podman"`). The pre-change call sites passed the binary and were therefore wrong for containerd; this migration's word form is the fix. `TestProbeBoundaryTakesTheEngineWord` pins both directions and the fallback, and the test logs the control: `a probe handed the BINARY "nerdctl" would invoke "podman" — the word is required`. The block's remedy is rejected with that evidence; the code keeps the word form.

Both fixes ride one appended commit on the same branch (no amend, no force-push).

### Round 3 — validator BLOCK, RCA, and disposition

The third verdict accepted round 2 and found ONE remaining contradiction: the tunnel read still
resolved its own selection. RCA and the missed control:

1. **`remove_tunnel.go` discarded the loader error and swallowed selection errors (fixed).** The
   body claimed the tunnel path surfaced an unreadable overlay and a retired engine word, but
   `resolveContainerTunnel` loaded and resolved the overlay itself (`dc, _ := …`; `if err != nil {
   return nil }`) — the silent-fallback class the migration deletes. The missed control: the
   per-site sweep counted `remove_tunnel.go` as migrated (it used the resolved WORD) without
   asking whether the SITE's error contract matched the claim; no test exercised the tunnel read's
   selection at all. Root fix: `charly remove` resolves the teardown selection ONCE and passes it

   the tunnel read has no selection error of its own to swallow and inherits the teardown
   contract exactly. `TestResolveContainerTunnelUsesThePassedSelection` pins it with fake
   `nerdctl`/`podman` executables: the probe runs the passed containerd selection and never
   podman.
