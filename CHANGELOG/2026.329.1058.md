# 2026.329.1058 — fix(service): judge the status table, not the init tool's aggregate exit code

## Summary

`charly service status` exited non-zero on a healthy deployment whose image declares a
run-to-completion service. The init tool's aggregate exit code cannot answer the question: it
exits 3 when ANY process is not `RUNNING`, and a one-shot that has finished is exactly that
(pod-immich's `immich-db-init` is `restart: no`, `start_sec: 0`, `exit_code: "0"`).

The verb now takes the captured table and the exit code from the host reply and judges them:

- every row `RUNNING`, or `EXITED` on a service the image declares run-to-completion → **success**;
- any `FATAL`/`BACKOFF`/`STOPPED`/`STARTING` row, an `EXITED` service the image does not declare
  that way, or output that is not a table → **the tool's failure stands**;
- a reply with no output (an older host) → nothing is judged, today's behaviour.

A `service` op's exit code now travels in the reply rather than as an error, so `start`, `stop`
and `restart` turn it back into one (`serviceRunVerdict`). Without that, moving the code into the
reply would have made a failing `restart` exit 0 — the regression this PR's shape has to avoid.

Carried with the code: the ordinary consumer dependency bump (`spec v0.2026329.803` for the reply's
`output`, `sdk v0.2026328.2210`), and `/charly-core:service` stating the verdict (the skill is
projected from `.agents/skills/service/SKILL.md` in this repo, so it moves here).


The fixture is deliberately minimal — fedora-minimal + layer-supervisord + the check base/stack
layers' proven `check-sleep` + `check-init-layer`'s one-shot — and carries **no build-time plugin
candy**, because the pinned plugin candies are exactly what a spec bump skews
(opencharly/plugin-example-builder#7). The one-shot runs for two seconds, which is what a real
migration does: supervisord treats a process that exits inside its start window as failed, so an
instantaneous fixture would model something no real one-shot is. That is a property of the fixture,
not of charly, and it needs no renderer change.

The three skips are the two build-context checks (not active in live mode) and one unrelated
listener probe; **the step under test is not among them**. They are reported as SKIP, never silently
passed. The round-4 comment on this PR carries the RCA that reconciles this run with the earlier
"step still exits 3" report: that run was a fixture whose one-shot exited inside supervisord's start
window and went FATAL; the product code is unchanged since `a3d8b32`. The NEGATIVE arm — a long-running row that is not `RUNNING` must keep the tool's
failure — is unit-proven (`TestServiceStatusHealthy`, `TestServiceStatusVerdict`: FATAL, STOPPED,
BACKOFF, an undeclared EXITED and unparseable output each keep the error); it is not driven in this
bed because stopping a service would poison the fixture's own follow-on steps.
